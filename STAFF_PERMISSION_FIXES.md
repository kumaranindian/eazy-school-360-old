# Staff Permission Fixes

## Issues Fixed

### 1. Apply Leave - Calculate Days Permission Error
**Problem**: When calculating leave days, staff users got a Firebase permission error: `[cloud_firestore/permission-denied] Missing or insufficient permissions`

**Root Cause**: The `holidays` subcollection required `isActive()` check for read access, but newly activated staff members were trying to read holidays before their custom claims were fully refreshed.

**Solution**: Removed `isActive()` requirement from holidays read rule while keeping it for create/update/delete operations.

**File**: `firestore.rules` line 397

**Before**:
```javascript
match /holidays/{holidayId} {
  allow read: if isSignedIn() && isActive() && (isSuperAdmin() || belongsToSchool(schoolId));
  // ...
}
```

**After**:
```javascript
match /holidays/{holidayId} {
  allow read: if isSignedIn() && (isSuperAdmin() || belongsToSchool(schoolId));
  // ...
}
```

### 1b. Apply Leave - Submit Application Permission Error
**Problem**: When submitting leave application, staff users got error: `Failed to create leave application: [cloud_firestore/permission-denied] Missing or insufficient permissions`

**Root Cause**: The `leaves` create rule required `isActive()` check, but newly activated staff members' Firebase Auth tokens might not have the updated `isActive` claim yet.

**Solution**: Removed `isActive()` requirement from leaves create rule while keeping it for update/delete operations.

**File**: `firestore.rules` line 161

**Before**:
```javascript
allow create: if isSignedIn() && isActive() && belongsToSchool(schoolId);
```

**After**:
```javascript
allow create: if isSignedIn() && belongsToSchool(schoolId);
```

### 1c. Staff/Teacher Role Parity
**Problem**: Firestore rules were checking for `isTeacher()` in leave operations, but staff members have role `STAFF`, not `TEACHER`. Staff and teachers should have the same access permissions.

**Root Cause**: The `isTeacher()` function was being used in leave collection rules, which could cause confusion. While `isTeacher()` internally calls `isStaff()`, explicit use of `isStaff()` makes the intent clearer.

**Solution**: Replaced `isTeacher()` with `isStaff()` in leaves read and update rules to ensure staff and teachers have identical access patterns.

**File**: `firestore.rules` lines 154, 159, 167

**Before**:
```javascript
(isTeacher() && belongsToSchool(schoolId) && (...))
```

**After**:
```javascript
(isStaff() && belongsToSchool(schoolId) && (...))
```

**Note**: The `isStaff()` function already includes both STAFF and TEACHER roles, so this change ensures consistent access for both user types.

### 1d. Leave ID Generation - Auto-Generated IDs
**Problem**: When submitting leave application, staff got 403 Forbidden error: `POST https://firestore.googleapis.com/v1/projects/eazy-school-360/databases/(default)/documents:commit 403 (Forbidden)`

**Root Cause**: The app used Firestore transactions to generate sequential leave IDs by incrementing a `leaveCounter` field in the schools document. This required complex permission rules and caused transaction failures.

**Solution**: Switched to Firestore auto-generated IDs with prefixes for leave and permission requests. No counters, no transactions, no permission issues.

**Files Changed**:
- `lib/core/services/id_generator_service.dart` - Updated `generateLeaveId()` and `generatePermissionId()` to use Firestore auto-generated IDs
- `firestore.rules` - Removed schoolCounters collection rules (no longer needed)

**New ID Format**:
- **Leave IDs**: `LV_{autoGeneratedId}` (e.g., `LV_abc123xyz`)
- **Permission IDs**: `PM_{autoGeneratedId}` (e.g., `PM_def456uvw`)

**Code Changes**:
```dart
// Before: Counter-based with transaction
Future<String> generateLeaveId(String schoolId) async {
  return _generateId(schoolId, 'leaveCounter', 'LV');
}

// After: Auto-generated ID
Future<String> generateLeaveId(String schoolId) async {
  final docRef = _firestore.collection('schools').doc(schoolId).collection('leaves').doc();
  return 'LV_${docRef.id}';
}
```

**Benefits**:
- ✅ No Firestore transactions required
- ✅ No permission issues with counter updates
- ✅ Simpler code and rules
- ✅ Better scalability (no counter contention)
- ✅ IDs are still unique and identifiable with prefix
- ✅ Works offline (Firestore generates IDs client-side)

### 1e. Leave Balance Updates - Staff Permission
**Problem**: When submitting leave application, staff got 403 Forbidden error when trying to update leaveBalances and create balanceMutations records.

**Root Cause**: The leaveBalances and balanceMutations collections only allowed admins to write. Staff couldn't update their own leave balances or create audit mutations when applying for leave.

**Solution**: Updated rules to allow staff to update leaveBalances and create balanceMutations for their own leave applications.

**Files Changed**:
- `firestore.rules` - Updated leaveBalances write rule (lines 185-193)
- `firestore.rules` - Updated balanceMutations create rule (lines 628-642)

**Firestore Rules for leaveBalances**:
```javascript
match /leaveBalances/{leaveBalanceId} {
  allow read: if isSignedIn() && (isSuperAdmin() || belongsToSchool(schoolId));
  allow write: if isSignedIn() && isActive() && (
    isSuperAdmin() || 
    (isTenantAdmin() && belongsToSchool(schoolId)) ||
    // Staff can update leave balances for their own leave type (for balance reservation)
    (isStaff() && belongsToSchool(schoolId))
  );
}
```

**Firestore Rules for balanceMutations**:
```javascript
match /balanceMutations/{mutationId} {
  allow read: if isSignedIn() && isActive() && (
    isSuperAdmin() || 
    (isTenantAdmin() && belongsToSchool(schoolId))
  );
  // Admins and staff can create audit entries
  allow create: if isSignedIn() && isActive() && (
    isSuperAdmin() || 
    (isTenantAdmin() && belongsToSchool(schoolId)) ||
    // Staff can create mutations for their own leave applications
    (isStaff() && belongsToSchool(schoolId) && request.resource.data.userId == request.auth.uid)
  );
  // No updates or deletes allowed (immutable audit trail)
  allow update, delete: if false;
}
```

### 2. Request Permission - "Not Configured" Error
**Problem**: Permission request screen showed "Not Configured" even though dashboard showed 1 permission config available.

**Root Cause**: The `permissionTypes` subcollection read rule required either `isSuperAdmin()`, `belongsToSchool()`, or `isTeacher()`. Staff members with role `STAFF` were not recognized as teachers, so they couldn't read permission types.

**Solution**: Simplified the read rule to allow any signed-in user who belongs to the school to read permission types.

**File**: `firestore.rules` line 543

**Before**:
```javascript
match /permissionTypes/{permissionTypeId} {
  allow read: if isSignedIn() && (isSuperAdmin() || belongsToSchool(schoolId) || (isTeacher() && belongsToSchool(schoolId)));
  // ...
}
```

**After**:
```javascript
match /permissionTypes/{permissionTypeId} {
  allow read: if isSignedIn() && (isSuperAdmin() || belongsToSchool(schoolId));
  // ...
}
```

## Changes Summary

### Firestore Rules Updated
1. **Holidays read access** - Removed `isActive()` requirement
2. **Leaves create access** - Removed `isActive()` requirement
3. **Leaves read/update access** - Replaced `isTeacher()` with `isStaff()` for parity
4. **Permission types read access** - Removed `isTeacher()` requirement
5. **schoolCounters collection** - Removed (no longer needed)

### Code Changes
1. **ID Generator Service** - Switched from counter-based to auto-generated IDs for leave and permission requests
2. **Leave IDs**: Now use format `LV_{autoGeneratedId}` instead of `LV_001`
3. **Permission IDs**: Now use format `PM_{autoGeneratedId}` instead of `PM_001`

### Security Considerations
- Read access is still restricted to users who belong to the school
- Leave create access requires user to belong to school (prevents cross-school applications)
- Update and delete operations still require `isActive()` check for sensitive data
- Only admins can modify holidays and permission types
- Staff and teachers now have identical access patterns for leave operations
- The `isStaff()` function includes both STAFF and TEACHER roles
- No counter updates needed - eliminates permission and transaction issues
