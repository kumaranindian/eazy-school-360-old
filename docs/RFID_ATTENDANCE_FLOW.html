1
ESP32 scans RFID card → gets UID
↓
2
ESP32 calls POST /mark-attendance with UID, deviceId, timestamp
↓
3
Middleware validates device key
↓
4
System fetches user from RFID mapping
↓
5

↓
6

↓
7

↓
8

🔌 API Endpoints

POST/register-rfid

Purpose: Register RFID card to a user

Body:

{ "schoolId": "school123", // Required "uid": "A1B2C3D4", // Required - RFID card UID "userId": "user456" // Required - User ID in school }

Headers:

x-device-key: "your-device-secret-key"

Response (201):

{ "success": true, "message": "RFID card registered successfully", "data": { "uid": "A1B2C3D4", "userId": "user456", "schoolId": "school123", "registeredAt": "2026-05-04T11:00:00Z" } }
POST/mark-attendance

Purpose: Mark attendance when RFID card is scanned

Body:

{ "schoolId": "school123", // Required "uid": "A1B2C3D4", // Required - RFID card UID "deviceId": "device001", // Required - Device ID "timestamp": 1714826400000 // Optional - Unix timestamp (ms) }

Headers:

x-device-key: "your-device-secret-key"

Response (201):

{ "success": true, "message": "Attendance marked successfully", "data": { "attendanceId": "att789", "schoolId": "school123", "userId": "user456", "uid": "A1B2C3D4", "scannedAt": "2026-05-04T11:00:00Z", "userDetails": { "userId": "user456", "name": "John Doe", "email": "john@school.com", "role": "TEACHER" }, "deviceId": "device001", "deviceName": "Main Entrance" } }
POST/register-device

Purpose: Register a new RFID scanning device

Body:

{ "schoolId": "school123", // Required "deviceId": "device001", // Required "deviceName": "Main Entrance" // Required }

Headers:

x-device-key: "admin-device-key" // Use existing admin device key

Response (201):

{ "success": true, "message": "Device registered successfully", "data": { "deviceId": "device001", "deviceName": "Main Entrance", "schoolId": "school123", "isActive": true, "deviceKey": "a1b2c3d4e5f6...", // 64-char hex string "createdAt": "2026-05-04T11:00:00Z" }, "warning": "Store the deviceKey securely. It will not be shown again." }

🔒 Security

⚠️ Important: All requests must include the x-device-key header with the device's secret key.

Security Layers

Layer Description
Device Key Validation Every request validated against stored device key in Firestore
Device ID Matching deviceId in body must match authenticated device
Device Status Check Inactive devices are rejected
RFID Status Check Inactive RFID cards cannot mark attendance
Duplicate Prevention 5-minute window prevents duplicate scans
Firestore Rules Server-side rules prevent unauthorized access

❌ Error Responses

401 Unauthorized
{ "success": false, "error": "UNAUTHORIZED", "message": "Missing x-device-key header" }
403 Forbidden
{ "success": false, "error": "FORBIDDEN", "message": "Invalid device key" }
404 Not Found
{ "success": false, "error": "RFID_NOT_FOUND", "message": "RFID card not registered" }
409 Conflict
{ "success": false, "error": "DUPLICATE_SCAN", "message": "Duplicate scan detected. Last scan was 2 minutes ago", "data": { "lastScanTime": "2026-05-04T10:58:00Z", "timeSinceLastScan": 120000 } }

⚡ Firestore Trigger

onAttendanceCreate - Automatically triggers when a new attendance record is created

Actions Performed:

  • Updates user's lastSeenAt timestamp
  • Updates user's lastSeenDevice field
  • Creates/updates daily attendance summary
  • Logs the attendance event
  • (Optional) Can trigger notifications

Benefits:

  • Automatic user activity tracking
  • Daily attendance summaries for reporting
  • Extensible for notifications/alerts
  • No additional API calls needed

✅ Best Practices

Security
  • Never expose device keys in client-side code
  • Store device keys securely (environment variables or secret manager)
  • Rotate device keys periodically
  • Use HTTPS for all API calls
Performance
  • Use server timestamps for consistency
  • Batch writes when possible
  • Implement proper indexing for queries
  • Monitor function execution time
Scalability
  • Functions auto-scale with Firebase
  • Idempotent operations prevent duplicate issues
  • Concurrent requests handled safely with transactions
  • Monitor and set appropriate function timeouts
