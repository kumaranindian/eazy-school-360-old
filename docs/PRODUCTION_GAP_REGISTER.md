# Eazy School 360 — Production Gap Register

Part of the Production Readiness Audit. See `docs/README.md` for the document index and `docs/FEATURE_READINESS_MATRIX.md` for the per-feature summary this register drills into.

**Severity**: P0 (blocker — must fix before production), P1 (critical — major functionality incomplete/unreliable), P2 (major — important functionality/UX issue), P3 (minor — non-blocking improvement).

**Status**: `Open` (not touched), `Fixed` (resolved this session, verified), `Documented` (known landmine, deliberately not touched — see rationale in the row).

## P0 — Blockers

| ID | Module | Feature | Issue | Impact | Root Cause | Recommended Fix | Dependencies | Status |
|---|---|---|---|---|---|---|---|---|
| GAP-001 | Core / Super Admin | Tenant activation | New self-signed-up schools are created `isActive: false` and there is **no reachable UI anywhere in the app** to activate them — the Super Admin dashboard shows hardcoded fake data and its "Add School"/management actions are no-ops. | Blocks the product's entire new-customer onboarding loop, independent of every other finding. | Super Admin dashboard was never finished; `SchoolManagementRepository` (which has `activateSchool`/`deactivateSchool` fully implemented) is referenced nowhere in the UI. | Wire the existing `SchoolManagementRepository` methods into a real Super Admin dashboard screen (pending-schools list, activate/deactivate actions). Backend logic already exists — this is a UI task. | None blocking — can start immediately. | Open |
| GAP-002 | RFID / Security | Device registration auth | `/register-device` had no authentication — any caller who knew a `schoolId` could self-register a device and receive a permanent, valid device key. | Full compromise of the RFID attendance subsystem: forged attendance, unmapped real cards. | Endpoint designed for "initial registration, no device key required" per its own docs, with no substitute authentication added. | **Fixed this session**: now requires a Firebase ID token from an admin of the target school. | — | **Fixed** |
| GAP-003 | Backend / Security | `standardizeAcademicYears`, `updateAllStudentPhoneNumbers` | Both Cloud Functions shipped with authentication checks fully commented out ("temporarily disabled for migration/testing"), live in production. | Unauthenticated bulk data mutation across an arbitrary school (academic-year fields; every student's/parent's phone number). | Debugging/migration shortcut never reverted. | **Fixed this session**: both re-enforce admin auth scoped to the target school. | — | **Fixed** |
| GAP-004 | Backend / Security | `setUserClaims` | Any authenticated user could set an arbitrary uid's custom claims to a client-supplied object — a direct privilege-escalation path (self-grant SUPER_ADMIN). | Complete authorization bypass if exploited. | No role check at all on the caller; claims trusted from the request body. | **Fixed this session**: restricted to SUPER_ADMIN callers; claims re-derived server-side, never trusted from the client. | — | **Fixed** |
| GAP-005 | Backend / Security | Cross-tenant scoping on 9 Cloud Functions | `approveLeave`/`rejectLeave`/`approvePermission`/`rejectPermission`/`adjustLeaveBalance`/`adjustPermissionBalance`/`mapRfidToStaff`/`listRfidCards`/`unmapRfidCard` checked the caller's admin role but not that the caller's `schoolId` matched the target `schoolId`. | An admin of one school could approve/reject/adjust leave and permission balances, or manage RFID cards, for a different school entirely. | Inline auth checks copy-pasted without the school-match line that a sibling function (`batchApproveLeaves`) did include. | **Fixed this session**: shared `assertAdminSchoolAccess` helper added and called in all 9. Not proven exhaustive — other functions with the same pattern may exist unfound. | — | **Fixed (where found)** |
| GAP-006 | Storage / Security | `teacher_documents`, `leave_attachments` rules | Both Storage paths allowed **any authenticated user from any school** to read (`teacher_documents`) or read+write (`leave_attachments`) another school's files. | Cross-tenant exposure of what are likely personal documents (ID proofs, certificates) and leave-request attachments; `leave_attachments` additionally permitted cross-tenant **writes**. | Rules deliberately "relaxed" per an in-file comment ("since custom claims may not be present for staff users") and never tightened back. | Added `belongsToSchool(schoolId)` checks (plus a self-access fallback on `teacher_documents` read, since that doesn't depend on the schoolId claim being populated), matching the pattern already used correctly in `payslips` and in `firestore.rules`'s own `leaves` collection scoping. | None — self-contained rules-file change. | **Fixed** (IMPL-10) — not yet deployed or live-tested; see Testing note in IMPLEMENTATION_PLAN.md |
| GAP-007 | Fee/Finance | Two parallel fee-structure systems | Legacy (`fee_repository.dart`) and v2 (`fee_structure_v2_repository.dart`) are both live, read by different screens, for the same student/school data. | A fee structure created in one system may be invisible to or inconsistent with screens reading the other — real risk of a family being billed incorrectly. | Incomplete migration from legacy to v2; migration path was documented as planned but never executed. | Product decision required: pick one system, migrate the other's data and screens, retire the loser. Not a quick patch. | Requires a data-migration plan and screen-by-screen rework — the largest single piece of remaining work in the Gap Register. | Open |
| GAP-008 | Fee/Finance | Bill deletion / ledger reversion | Deleting a bill and reversing its effect on the student's ledger are separate, non-transactional writes; a reversal failure is caught and only `print()`-logged, while the UI still reports success. | A transient error leaves the bill gone but the student's balance permanently wrong, invisibly to the admin. | No transaction wraps the two operations; error handling swallows rather than surfaces the failure. | Wrap bill-delete + ledger-reversal in a single Firestore transaction; surface any failure to the admin instead of a false success message. | None blocking. | Open |

## P1 — Critical

| ID | Module | Feature | Issue | Impact | Root Cause | Recommended Fix | Dependencies | Status |
|---|---|---|---|---|---|---|---|---|
| GAP-009 | Finance / Payroll | Payroll admin UI | Live admin dashboard's Payroll nav item routes to a "Coming Soon" placeholder instead of the fully-built `PayrollManagementScreen`. | Salary structures can never be entered, payroll can never be run — feature is 100% inert despite correct backend code. | A one-line navigation wiring mistake/placeholder never replaced. | Swap the placeholder for `const PayrollManagementScreen()` in `admin_dashboard_screen.dart`; then test the full salary-structure → payroll-run → payslip flow end to end. | None — smallest-effort, highest-payoff fix in this entire register. | Open |
| GAP-010 | Fee/Finance | Razorpay online payment | No backend Cloud Function exists for order creation or signature verification; no UI references it. | Online payment is not a real capability despite data-model support (`PaymentGateway.RAZORPAY`) and historical docs claiming "implementation complete." | Feature was scoped and partially modeled but the actual Cloud Functions were never built. | Build the Razorpay order-creation + webhook-verification Cloud Functions, then wire a "Pay Online" entry point into the payment dialog. Net-new backend work, not a fix. | Requires a live Razorpay merchant account/API keys before it can be tested. | Open |
| GAP-011 | Academic Year | Student promotion | `StudentPromotionScreen` is fully implemented but referenced nowhere in the live app. | Year-end student promotion cannot be performed through the app. | Same class of gap as GAP-009 — a finished feature never wired into navigation. | Add a reachable entry point (likely from `AcademicYearManagementScreen` or the admin dashboard) to `StudentPromotionScreen`. | Low — mostly a navigation change; verify the promotion logic itself with a dry run first given no automated tests cover it. | Open |
| GAP-012 | Backend / Data Integrity | Leave/permission trigger idempotency | Deployed `onLeaveStatusChange`/`onPermissionStatusChange` had no guard against Cloud Functions' at-least-once retry delivery — a retry could double-apply a balance mutation. | Silent leave/permission balance corruption on any trigger retry (which Cloud Functions performs automatically on transient failure). | The correct, idempotency-safe implementation existed in unused sibling files (`atomic-leave-approval.js` etc.) but was never the one actually deployed. | **Fixed this session**: ported the `processedAt` guard into the live triggers, set inside the same transaction as the balance write. | — | **Fixed** |
| GAP-013 | Auth | Password/credential logging | Raw and generated passwords were printed to console on every login and staff-account creation. | Credential leakage into device/system logs. | Debug-era `print()` statements never removed. | **Fixed this session**: removed from `auth_provider.dart`, `staff_management_repository.dart`, `teacher_repository.dart`. | — | **Fixed** |
| GAP-014 | Fee/Finance | Bill/Invoice numbering | `getNextBillId()` is a plain max-existing-value+1 query, not a Firestore transaction — collision-prone under concurrent bill creation. | Duplicate bill IDs possible when two bills are created at nearly the same time (e.g. two staff at the front office). | Numbering pattern wasn't given the same transactional treatment as the (correctly-built) receipt counter. | Rewrite `getNextBillId()`/expense equivalent to use a transactional counter doc, matching `term_fee_payment_repository.dart`'s pattern. | None blocking. | Open |
| GAP-015 | Backend / Security | Backend authorization layer unused | `backend-authorization.js` implements a complete, well-designed role/tenant check class that **no deployed function actually calls**. | The documented "authoritative backend layer" of the 3-layer RBAC design provides zero real protection; every function reimplements its own (previously inconsistent) inline check instead. | Module appears to have been written as the intended architecture, then bypassed during implementation without anyone reconciling the two. | Either wire it into every sensitive function's entry point, or formally retire it and rely on the (now more consistent) inline checks — a decision, not a quick patch either way. | Touches every Cloud Function — needs careful, function-by-function regression testing if wired in. | Documented, not fixed |
| GAP-016 | Frontend / Security | Client-side route guards | `RouteGuard` widget only wraps the 4 top-level dashboard screens; none of the ~60 feature screens beneath them re-check access on entry, relying entirely on the navigating button having been gated. | If any button's gating is missed, or a screen becomes reachable by a future navigation path, there's no independent check. | The `go_router`-based route-level RBAC design (`app_router.dart`) exists but is entirely dead code — the app runs on manual `Navigator.push` instead. | Either revive the `go_router` implementation properly, or add a lightweight per-screen guard check that doesn't depend on the caller having gated correctly. | Larger navigation-layer refactor. | Documented, not fixed |
| GAP-017 | Fee Management | Late fee calculation | Full `LateFeeRule`/`LateFeeType` (FIXED/PERCENTAGE/DAILY) schema exists, but no code ever calculates a late fee from a due date — `lateFeeApplied` is only ever carried forward unchanged, and there's no manual-entry UI either. | Schools cannot charge late fees at all despite the data model appearing to support it — a silent functional gap that could surprise anyone relying on the schema's presence as proof of the feature. | Calculation engine was modeled but never implemented. | Implement the calculation (due-date-crossing check + `LateFeeType` branch) as a scheduled job or on-read computation, or provide a manual-entry path if automatic calculation isn't wanted. | Depends on GAP-007's fee-system consolidation decision (which system should own this logic). | Open |
| GAP-018 | Payment | Refunds | Zero refund capability anywhere in the codebase. | Cannot reverse a payment other than the non-atomic bill-deletion flow (GAP-008). | Never built. | New feature: refund recording, ledger reversal, and (if online payments are ever built) gateway-side refund API integration. | Should be designed alongside GAP-008's fix, since both touch ledger-reversal logic. | Open |

## P2 — Major

| ID | Module | Feature | Issue | Impact | Root Cause | Recommended Fix | Dependencies | Status |
|---|---|---|---|---|---|---|---|---|
| GAP-019 | Parent Portal | No parent-initiated payment | No screen exists for a parent to pay fees themselves in-app; all payment recording is admin/finance-side. | A typical parent-portal expectation (self-service payment) is absent. | Tied to Razorpay never being built (GAP-010) — there's no gateway for a parent to pay through even if a button existed. | Build after GAP-010; add a "Pay Now" entry point in the parent's fee view once a gateway exists. | GAP-010. | Open |
| GAP-020 | Finance | Reconciliation | No reconciliation feature exists — only UI text telling the admin to reconcile manually. | Manual, error-prone reconciliation with no system support. | Never built. | Design and build a reconciliation report/tool comparing recorded payments against bank/gateway statements. | None blocking, but low value until GAP-010 (online payments) exists, since manual cash/UPI reconciliation needs differ from gateway reconciliation. | Open |
| GAP-021 | Database | Unbounded student-list queries | Main student list `.snapshots()` queries have no `.limit()` — full-roster fetch on every screen open. | Performance/cost risk for large schools; no pagination UI exists to mitigate it even if a limit were added. | Pagination was never implemented for this screen. | Add `.limit()` + a "load more"/paginated UI pattern, consistent with whatever pattern (if any) other list screens use. | None blocking. | Open |
| GAP-022 | Database | `getSchoolStaff` `.limit(10000)` | A hardcoded large limit stands in for real pagination on the staff list. | Same class of risk as GAP-021, smaller ceiling. | Same as above. | Same fix pattern as GAP-021. | None. | Open |
| GAP-023 | RFID | No rate-limiting / duplicate-scan protection | `attendanceController.js` deliberately removed duplicate-scan protection (per its own code comment); no throttling exists. | A legitimately-registered but compromised device could flood-write attendance records. | Protection removed at some point to "allow multiple scans," apparently without a replacement throttle. | Add a minimum-interval-between-scans check per card/device, distinct from a hard duplicate block. | GAP-002's fix (device auth) reduces but doesn't eliminate this risk — a legitimate device can still misbehave or be compromised after registration. | Open |
| GAP-024 | Backend | `functions/lib/` vs `functions/src/` build fragility | Build script's `xcopy` step is Windows-only; a non-Windows contributor running `tsc` alone silently leaves compiled JS stale relative to source. | Risk of deploying stale logic for the modules that go through this copy step (e.g. WhatsApp reminders). | Build tooling written for a Windows-only workflow. | Replace `xcopy` with a cross-platform copy step (`cpx`, `shx cp`, or a small Node script) in `package.json`'s `build` script. | None blocking. | Open (documented in `CLAUDE.md`) |
| GAP-025 | Repository hygiene | `node_modules` committed to git | 44,828 files under `node_modules/`/`functions/node_modules/` are tracked by git; no `.gitignore` entry excludes them. | Repo bloat, slow clones, unreviewable dependency-update diffs, no CI to catch it. | `.gitignore` was never updated to exclude `node_modules`. | Add `node_modules/` to `.gitignore`; `git rm -r --cached` both directories. | Coordinate timing — a large history-changing commit affects every branch/PR in flight. | Open |
| GAP-026 | Auth | Staff-account creation pattern inconsistency | `createAdmin()`/`createFinanceAdmin()` and bulk upload still use an older temp-password-export pattern; newer staff-creation path uses random-password + reset-email. | Inconsistent security posture across account-creation paths; the older pattern is also the (now-fixed) source of the password-logging bug. | Migration to the newer pattern was partial. | Migrate the remaining creation paths to the reset-email pattern for consistency. | None blocking. | Open |
| GAP-027 | Fee Management | Discounts/concessions are flat-amount only | `ConcessionCategory` models category metadata with no percentage field; the actual discount is a flat amount on the ledger. | Cannot express a percentage-based concession (e.g. "10% sibling discount") without manual amount calculation by the admin. | Model was likely intended to support percentage-based rules but the calculation side was never built. | Add a percentage option to the concession application logic if percentage-based discounts are a requirement. | Product decision on whether this is actually needed. | Open |
