# Eazy School 360 — Codebase Analysis

Generated by a full-repository review (Flutter frontend, Cloud Functions backend, and the project's ~35 historical implementation docs). See `CLAUDE.md` for day-to-day dev commands and the intended architecture; this document records the state actually found in the code, including bugs and security issues.

## 1. Executive summary

The app is functionally broad (staff/leave/permission/attendance/RFID/finance/academic-year modules) and the intended architecture (clean layering, three-layer RBAC, per-tenant Firestore scoping) is sound on paper. In practice:

- **The backend's authoritative authorization layer is never called.** `functions/src/security/backend-authorization.js` — documented as the "authoritative" RBAC check — is dead code; every real Cloud Function reimplements its own inline, inconsistent role check instead.
- **Two exported Cloud Functions have authentication/authorization commented out** ("temporarily disabled for migration/testing") and are live in production, allowing unauthenticated bulk data mutation.
- **The RFID attendance subsystem has a full authentication bypass**: device self-registration requires no credentials, handing out a valid device key to anyone who can reach the HTTPS endpoint.
- **Several admin-facing Cloud Functions and one Flutter repository skip `schoolId` scoping**, breaking cross-tenant isolation — the one hard security invariant this multi-tenant app is supposed to guarantee.
- **The Flutter app logs raw and generated passwords to the console** on every login and every staff-account creation.
- **The go_router-based route-guard stack is entirely dead code** (the app uses `MaterialApp` + manual `Navigator.push`, not `MaterialApp.router`), so its route-level RBAC checks provide zero actual protection; real protection is only 4 top-level dashboard screens wrapping themselves in a `RouteGuard` widget, with no independent check on the ~60 feature screens beneath them.
- The codebase carries substantial **duplication and drift**: two parallel dashboard folders, two parallel fee-structure systems (legacy + v2) both live and read by different screens, two independently-maintained "apply leave"/"request permission" screens, and a security-relevant Firestore-rules copy (`firestore.rules` at repo root) that has already diverged from the one actually deployed (`firebase/firestore.rules`).
- The project's own `.md` docs directly contradict each other on the status of at least two subsystems (RFID frontend, and whether the leave-balance architecture is Cloud-Functions-backed or client-only) — a sign some of this was never resolved, only documented twice.

None of the above required exploiting anything exotic — all findings came from reading the code that's actually wired into `functions/index.js` and `lib/main.dart`.

## 2. Architecture (as built, not just as intended)

Layering, environments, and the documented RBAC design are covered in `CLAUDE.md`. Two corrections to that intended picture, found during this review:

- **The backend RBAC layer is decorative.** `functions/src/security/backend-authorization.js` is referenced only by itself; no deployed function calls it. Every "protected" callable/trigger has its own inline `db.collection('users').doc(uid).get()` + role-string check, and several of those inline checks (below) don't scope by `schoolId` the way `CLAUDE.md`'s stated convention requires.
- **The Flutter route-guard stack is decorative.** `lib/core/routing/app_router.dart` (and the `lib/presentation/dashboards/` — with "s" — screens it routes to) is never reached at runtime; `lib/main.dart` builds a plain `MaterialApp` with manual `Navigator.push` navigation. Actual UI-level protection is the `RouteGuard` widget from `lib/core/security/route_guard.dart`, applied only to the four top-level dashboard screens.
- There are **two competing multi-tenancy storage strategies** in Firestore: most collections live under `schools/{schoolId}/...` (structurally tenant-isolated), but `leave_types` and `teachers` are flat top-level collections filtered by a `schoolId` field — and some single-document lookups against those two collections skip the filter entirely (§5).

## 4. Critical security findings (live in production code)

Ordered by severity.

1. **Unauthenticated RFID device self-registration — full subsystem auth bypass.**
   `functions/src/rfid-attendance/index.js:32` + `controllers/deviceController.js:18`. `POST /register-device` on the public `rfidApi` HTTPS function only runs the generic body-shape check (`validateRequest`), not `validateDeviceKey`. Anyone who knows or guesses a `schoolId` can self-register a device and receive a valid `deviceKey` back — which then unlocks `/register-rfid`, `/unmap-rfid`, and `/mark-attendance` for that school. An attacker can forge attendance records or unmap real staff/student RFID cards with zero credentials.

2. **`standardizeAcademicYears` has authentication fully commented out.**
   `functions/src/data-cleanup.js:70-79`, exported at `functions/index.js:36-44`, public HTTPS with CORS `*`. The auth/admin-role check is commented "temporarily disabled for migration purposes" and never re-enabled. Any unauthenticated POST with a `schoolId` triggers bulk writes across that school's fee structures/ledgers.

3. **`updateAllStudentPhoneNumbers` has authentication fully commented out.**
   `functions/src/student-phone-update.js:23-32`, exported at `functions/index.js:49`. Both the `context.auth` check and the admin-role check are commented "temporarily disabled for testing purposes." Any caller can overwrite every student's/parent's phone number for an arbitrary `schoolId`. Docstring says "for testing/demo purposes"; it is nonetheless exported to production.

4. **The documented authoritative backend-authorization layer is never invoked.**
   `functions/src/security/backend-authorization.js` (`BackendAuthorization.validateRequest`, `createTenantSafeQuery`, `createUserScopedQuery`) is referenced only inside its own file. Every real function reimplements its own inline role check instead — meaning:
   - `setUserClaims` (`functions/index.js`, inline) lets **any authenticated caller set an arbitrary uid's custom claims to a client-supplied object** — a privilege-escalation primitive (a STAFF account could grant itself `role: 'SUPER_ADMIN'`), with no role check at all on the caller.

5. **Cross-tenant scoping gaps in `leave-permission-management.js`.**
   `functions/src/leave-permission-management.js:147-241, 527-621, 695-753, 856-914` (`approveLeave`, `rejectLeave`, `approvePermission`, `rejectPermission`, `adjustLeaveBalance`, `adjustPermissionBalance`) check only that the caller's role is an admin role — never that `userData.schoolId === data.schoolId`. Contrast with `leave-management.js:465`'s `batchApproveLeaves`, which does check this. An ADMIN of School A can approve/reject/adjust balances for School B by passing its `schoolId`.

6. **Same cross-tenant gap in RFID admin functions.**
   `functions/src/student-phone-update.js:238-366` (`mapRfidToStaff`, `listRfidCards`, `unmapRfidCard`) — role-only check, no verification the admin's own `schoolId` matches the target `schoolId`.

7. **Device keys stored/compared in plaintext, non-constant-time.**
   `functions/src/rfid-attendance/middleware/deviceAuth.js:76` uses plain `!==` (timing side-channel, low practical severity given finding 1) and stores/queries device keys in cleartext in Firestore (`deviceAuth.js:49`) — any Firestore export/backup or rule misconfiguration leaks live device credentials directly.

8. **Deployed leave/permission triggers lack idempotency protection that exists in unused sibling code.**
   The live `onLeaveStatusChange` / `onPermissionStatusChange` (`leave-management.js:229-331, 811-915`) have no "already processed" guard. The *unused* `atomic-leave-approval.js` / `atomic-permission-approval.js` implementations do have one (an `afterData.processedAt` check plus a re-read inside the transaction). Since Cloud Functions automatically retries triggers on transient failure, the live code can double-apply a balance mutation (double-deduct or double-restore leave/permission days) on retry.

### Flutter-side credential leaks

9. **Raw password logged on every login.** `lib/core/providers/auth_provider.dart:113-115` prints the user's password length and the raw password itself, unconditionally (no debug-mode guard) — a plaintext credential leak into device/system logs.

10. **Generated temporary passwords logged in plaintext.** `lib/data/repositories/staff_management_repository.dart:931,957` and `lib/data/repositories/teacher_repository.dart:218` print auto-generated staff/teacher account passwords to the console.

11. **`FirebaseRulesVerifier`/`FirebaseIndexesVerifier` are non-functional stubs presented as a real security gate.** `lib/main.dart:113-160` treats a `false` result from these as "refuse to start the app," but `firebase_rules_verifier.dart:79-83` just `await`s a 500 ms delay and unconditionally returns success — it can never fail. `lib/main.dart:118` also passes the literal unfilled placeholder `'your-firebase-project-id'` (this is the dead `lib/main.dart` entry point, not the real per-environment ones — see `CLAUDE.md` — but it's still shipped code).

## 5. High-severity: tenant isolation / clean-architecture bugs (non-Functions)

- **`LeaveTypeRepository.isNameUnique` queries across ALL schools.** `lib/data/repositories/leave_type_repository.dart:176-194` has no `schoolId` filter at all, unlike the correctly-scoped `getLeaveTypeByName` in the same file and `PermissionTypeRepository.isNameUnique`. Currently unused, but a live trap if wired up.
- **`leave_types`/`teachers` single-document lookups skip the `schoolId` filter.** `leave_type_repository.dart:40-54` (`getLeaveTypeById`) and `teacher_repository.dart:63-77` (`getTeacherById`) rely entirely on Firestore rules for isolation since the query itself doesn't scope by tenant — inconsistent with the rest of the app's `schools/{schoolId}/...` subcollection pattern.
- **27 presentation-layer files call `FirebaseFirestore.instance` directly**, bypassing repositories and re-implementing `schoolId` scoping ad hoc. Notable: `finance/screens/student_fee_management_screen.dart:54-121`, `finance/screens/bill_management_screen.dart` (25 occurrences), `staff/screens/staff_student_ledger_screen.dart:62-86`, `finance/widgets/multi_allocation_payment_dialog.dart`, `admin/screens/whatsapp_settings_screen.dart:76-126`, `admin/screens/school_settings_screen.dart:55-75`. Every such call site is a place someone could forget the tenant filter.
- **Bill deletion and ledger reversion are non-atomic, and failures are silently swallowed while the UI reports success anyway.** `finance/screens/bill_management_screen.dart:1781-2066`: `_deleteBill` marks the bill deleted in one write, then does several independent read-then-update calls against `student_fee_details`/`studentFeeLedgers` (classic lost-update race under concurrent deletes), wrapped in a catch that only `print()`s the error (line 2039-2041) before still showing "Bill deleted & Rs.X reverted" (2049-2060) regardless of whether the reversion succeeded. A transient error leaves the bill gone but the student's balance permanently wrong, with no admin-visible error.
- **Fully-swallowed empty catch blocks hide query failures from the admin.** `finance/screens/student_fee_management_screen.dart:69,95,121` (`catch (_) {}` around class/section/student loads — likely a missing-composite-index failure mode, renders as empty dropdowns with no explanation) and `bill_management_screen.dart:133-135` (`print()`-only, so a partial fetch failure makes bills silently vanish from the list).
- **`staff_management_repository.dart:52-154`'s `getSchoolStaff` — a read path called on every Staff Management screen load — has unawaited debug probing and a live write baked in**: it fire-and-forget writes `users/{uid}.status = 'ACTIVE'` when it finds a null status, force-refreshes the ID token, and writes-then-deletes a literal `test-doc`/`test-doc-retry` document under the school's `staff` subcollection "to test write permissions" — none of it awaited, so it races the real listener query set up immediately after.
- **`auth_provider.dart:205-215`** bypasses Riverpod's `StateNotifier` change detection with a lint-suppressed `super.state = ...` write to force a rebuild after `switchSchool` — a symptom that `AuthState` (an unchanged enum across a school switch) doesn't actually notify listeners of the switch; fragile rather than an event-driven state change.

## 6. Medium severity: dead code, duplication, and drift

11. **The entire go_router route-guard stack is dead code.** `lib/main.dart` uses `MaterialApp` with manual `Navigator.push`, never `MaterialApp.router` — so `appRouterProvider`/`AppRoutes`/`app_router.dart`'s internal `RouteGuard` class provide no real protection, and `lib/presentation/dashboards/` (the "s" folder) is effectively unreachable.
12. **`lib/presentation/widgets/enhanced_admin_dashboard.dart`** — 700+ unreferenced lines with direct Firestore calls and debug prints.
13. **`lib/presentation/dashboard/screens/admin_dashboard_screen_old.dart`** — 850+ unreferenced lines, left next to the live screen.
14. **Two parallel, both-actively-used fee-structure systems.** Legacy `fee_structure.dart`/`fee_repository.dart` still powers `student_directory_screen.dart`, `fee_collection_screen.dart`, `upload_sheet_screen.dart`, `student_fee_management_screen.dart`, `student_management_screen.dart`, `admin_dashboard_screen.dart`; the newer `fee_structure_v2.dart`/`fee_structure_v2_repository.dart` powers `fee_structure_editor_screen.dart`, `fee_structure_list_screen.dart`, `fee_structure_bulk_import_screen.dart`, `assign_fee_structure_screen.dart`, `student_fee_ledger_repository.dart`. A fee structure created via one system may not be visible to or consistent with the other, for the same student/school.
15. **Independently-maintained duplicate "apply leave"/"request permission" screens.** `presentation/leave/screens/apply_leave_screen.dart` (569 lines) vs. `presentation/staff/screens/apply_leave_screen.dart` (838 lines, the one actually reached from the live staff dashboard); same split for permission screens (614 vs. 870 lines). A validation fix applied to one is easy to miss in the other.
16. **Duplicate student-directory/management screens** (`finance/screens/student_management_screen.dart` vs. `admin/screens/student_directory_screen.dart` / `student_directory_with_ledger_screen.dart`), tracking the same legacy/v2 fee-system split.
17. **Naming collision between two unrelated `RouteGuard` classes** — the dead one in `app_router.dart:24` and the live widget in `core/security/route_guard.dart:9`.
18. **No independent access gate on ~60 feature screens.** The live `RouteGuard` widget wraps only the 4 top-level dashboards; screens reached from them (everything under `admin/screens/`, `finance/screens/`, `staff/screens/`) trust that the navigating button was itself permission-gated, with no re-check on entry.
19. **`functions/index.js:99-114` exports `dailyAttendanceFinalizer`, which is `undefined`** — destructured from `./lib/index`, whose corresponding export is commented out ("now handled by `combined-daily-jobs.js`"), a stale leftover from a refactor.
20. **`functions/src/leave-management.js:337-436`'s `onLeaveCreate`** duplicates `handleLeaveApplicationCreate`'s balance-reservation logic on the same document path, with different (auto-create-if-missing) semantics. Not currently exported, but a landmine if anyone adds it to `functions/index.js` — both triggers would fire on every new leave and double-reserve the balance.
21. **`functions/lib/` vs `functions/src/` is currently in sync but the build process is fragile.** The `xcopy`-based build (`CLAUDE.md` already flags this as Windows-only) means a non-Windows contributor running `tsc` alone would leave `lib/src/*.js` stale relative to `src/*.js`, and `functions/index.js:29` requires `./lib/src/whatsapp-fee-reminders` directly — a future edit without a working copy step would silently deploy stale WhatsApp-reminder logic.
22. **`functions/src/rfid-attendance/controllers/attendanceController.js`** has no validation on `rfidTag`/`schoolId` shape before using them as Firestore doc IDs, and (per its own code comment) duplicate-scan protection was deliberately removed — combined with finding 1, a rogue device can flood-write unlimited attendance records with no throttling.
23. **`firestore.rules`/`firestore.indexes.json` exist both at repo root and under `firebase/`, and have already diverged** — see `CLAUDE.md` for which copy is actually deployed (`firebase/`). Editing the wrong copy is a live risk for anyone not aware of this.

## 7. Lower-severity issues

- **686 `print()` call sites across 51 Flutter files**, none gated by `kDebugMode`, versus a dedicated `lib/core/utils/app_logger.dart` used in only 2 places. This is how the password-leak findings (§4.9–4.10) shipped in the first place.
- **Hardcoded prod Firebase console link with a literal project ID** in `lib/data/repositories/concession_category_repository.dart:46` — wrong for dev/test/uat environments.
- **`functions/src/rfid-attendance/utils/logger.js:5-17`** logs full request bodies (`schoolId`, `deviceId`, `uid`) on every API call with no log-level gating — a cost/PII-exposure smell rather than a hard bug.
- **`functions/fix-existing-user-claims.js`** duplicates claim-computation logic from `functions/index.js` in a standalone, undeployed script — no shared module, so the two copies can drift (no drift found currently).

## 8. Known historical bugs (already fixed — logged here for pattern-awareness)

From `CRITICAL_FIXES_APPLIED.md`, `FIXES_VERIFICATION.md`, `PERMISSION_LEAVE_FIXES.md`, `STAFF_PERMISSION_FIXES.md`, `PERMISSION_MANAGEMENT_IMPLEMENTATION.md`:

- **Leave cancellation permission-denied**: `firestore.rules` only allowed `pending→cancellationRequested`, not the direct `pending→cancelled` a teacher needs when cancelling their own not-yet-approved leave. Fixed in rules + admin UI.
- **Permission-request time-picker crash**: end-time computed as `TimeOfDay.now().hour + 2` overflowed past 24 after ~10 PM. Fixed with `% 24`.
- **A cluster of staff-facing permission-denied bugs**, all traced to an `isActive()` Firestore-rule requirement that staff accounts (stale `isActive` field / unrefreshed custom claims) didn't satisfy: blocked reads of `permissionConfig`/`permissionTypes`/`holidays`, blocked creates of `leaves`/`permissionRequests`, an `isTeacher()` vs `isStaff()` mismatch excluding STAFF-role users, and a transaction-based leave/permission ID counter that 403'd under contention (replaced with Firestore auto-IDs, removing the `schoolCounters` collection entirely). **Fixed by loosening `isActive()` requirements** on several read/create rules — deliberate, but worth revisiting given how many of the §4/§5 findings above are also rules/auth-scoping issues.
- **`PermissionStatus` enum missing cancellation states** — added, and the repository-layer cancellation/balance-restoration logic was completed, but **the docs explicitly flag the UI side (teacher cancel button, admin cancellation banner, dashboard cancellation-count cards) as not yet built** — worth checking against current `lib/presentation/permission/` and `lib/presentation/staff/` for whether this landed.

## 10. Contradictions in project documentation

- **RFID frontend build status.** `RFID_SYSTEM_SUMMARY.md`/`RFID_ATTENDANCE_SYSTEM_IMPLEMENTATION.md` say the UI layer is "pending, 2-3 weeks." `IMPLEMENTATION_COMPLETE_SUMMARY.md`/`FRONTEND_IMPLEMENTATION_GUIDE.md` (apparently later) say it's built and "ready to use" modulo a few hours of repository wiring — and even internally waver between "100% complete" and "95% complete." The Flutter survey confirms RFID admin screens do exist in `lib/presentation/admin/`, so the earlier "pending" docs are at least stale; whether the *later* docs' claims of full readiness are accurate wasn't separately verified line-by-line.
- **Leave-balance/activation architecture: Cloud-Functions-backed vs. client-only — a direct contradiction, now resolved by this review.** `USER_ACTIVATION_IMPLEMENTATION.md`/`STAFF_PERMISSION_FIXES.md` describe a deliberately Cloud-Functions-free design (client writes `leaveBalances`/`balanceMutations` directly, to stay on the Firebase Spark free plan) versus `DEPLOYMENT_INSTRUCTIONS.md` describing backend-only writes via `functions/src/leave-management.js`/`auth-management.js`, blocked on Blaze-plan billing. **This review confirms the Cloud-Functions-backed design is what's actually deployed** (`functions/index.js` exports exactly those handlers) — so `DEPLOYMENT_INSTRUCTIONS.md` reflects reality and the "stay on Spark, client-only" docs describe an abandoned earlier plan. Firestore rules for `leaveBalances`/`balanceMutations` should be checked for leftover client-write permissions from the abandoned design (the §8 "loosened `isActive()`" fixes touched exactly these collections).
- **Academic-year completion percentage** climbs cleanly across a doc sequence (70%→90%) rather than truly contradicting — flagged in case the "final" doc isn't actually the latest state in the repo's history.

## 11. Suggested priority order

1. Fix the two commented-out-auth functions (§4.2, §4.3) and the RFID device-registration bypass (§4.1) — these are unauthenticated production data-mutation paths, the highest-impact items in this report.
2. Lock down `setUserClaims` (§4.4) — currently a privilege-escalation primitive for any authenticated user.
3. Add the missing `schoolId` cross-tenant checks in `leave-permission-management.js` and the RFID admin callables (§4.5, §4.6).
